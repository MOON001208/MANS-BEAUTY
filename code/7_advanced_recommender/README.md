# 남성 베이스 메이크업 수집·추천 파이프라인

현재 운영 코드는 이 디렉터리의 Python 파이프라인과 `web`입니다. 이전 단계의 노트북·Gemini 실험 코드는 운영 작업에서 실행하지 않습니다.

## 실행 환경

Python 3.13, Node.js 24. 저장소 루트에서 가상환경을 만들고 설치합니다.

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r code/7_advanced_recommender/requirements.txt
```

이 디렉터리의 `.env.example`을 `.env`로 복사한 뒤 서버 전용 `SUPABASE_SECRET_KEY`를 설정합니다. `web/.env.local`에는 URL과 공개용 publishable 키만 넣습니다. 실제 `.env`는 Git에 포함하지 않습니다.

처음 연결하는 DB에는 `migrations/20260917_pipeline_security.sql`을 Supabase SQL Editor에서 먼저 적용합니다. 상품·리뷰 행은 삭제하지 않으며, 공개 계정의 쓰기 권한과 리뷰 작성자 닉네임 조회 권한을 제거합니다. 노출된 관리자 키 자체는 별도 폐기해야 합니다.

## 수집과 갱신

아래 명령은 저장소 루트 기준입니다. 기본 실행은 DB에 쓰지 않는 dry-run입니다.

```powershell
# 특정 상품의 연결·응답 확인
.venv/Scripts/python.exe code/7_advanced_recommender/run_pipeline.py --product A000000198001 --max-review-pages 3
# 신상품 탐색, 리뷰 적재, 추천 프로필 갱신
.venv/Scripts/python.exe code/7_advanced_recommender/run_pipeline.py --write
# 기존 저장 리뷰만 다시 분석
.venv/Scripts/python.exe code/7_advanced_recommender/run_pipeline.py --write --profiles-only
```

- 현재 베이스 메이크업 카테고리를 신상품순·인기순으로 탐색하고 상품 상세의 `menCategoryFlag`와 분류를 확인합니다. 모든 남성 스킨케어 카테고리까지 확장한 수집기는 아닙니다.
- 리뷰는 모바일 웹의 공개 cursor API에서 최신순·도움순·높은 평점순·낮은 평점순으로 수집합니다. 공식 제공 SDK나 보장된 외부 API가 아니므로 사이트 변경 시 점검이 필요합니다.
- 리뷰 ID로 중복 제거합니다. 기존 ID가 나왔다고 탐색을 끝내지 않습니다. 세트·리필의 연결 리뷰는 원본 상품 ID를 보존하고, 해당 상품을 확인한 뒤 저장합니다. 이미 저장된 ID의 내용·귀속은 자동 덮어쓰지 않습니다.
- 페이지 저장 성공 후 커서를 기록합니다. 다음 실행은 최신 첫 페이지를 확인한 다음 이전 커서부터 이어갑니다. 오래 갱신하지 않은 상품을 먼저 처리해 특정 상품에 실행 시간이 계속 소모되지 않게 합니다.
- 기본 요청 간격은 2초, 수집 시간 예산은 90분입니다. 401/403, 반복된 429, 로그인 요구, 반복 커서를 감지합니다. 접근 제한을 우회하지 않습니다. 사이트 제한으로 전체 리뷰를 확보하지 못할 수 있습니다.
- `.pipeline-cache`에 커서·탐색 캐시·실행 보고서를 기록합니다. Git에 포함하지 않습니다. `--fresh`는 저장 커서 대신 처음부터 탐색합니다.
- 성분표가 차단되거나 여러 옵션의 성분이 섞이면 추정하지 않습니다. 확인된 성분표가 없으면 성분 관련 판정을 제공하지 않습니다.

GitHub Actions `Scheduled Crawler Update`는 매주 월요일 09:00 KST에 **저장된 리뷰의 프로필만 갱신**합니다. GitHub 호스팅 서버의 올리브영 요청이 403으로 차단되어, 수집은 사용자가 PC에서 위 명령으로 수동 실행하는 구성입니다. PC에 자동 작업은 등록하지 않습니다. `SUPABASE_URL`, `SUPABASE_SECRET_KEY` Secrets가 필요합니다. 수동 Actions 실행의 `collect_reviews`는 기본 false이며 접근 가능한 실행 환경에서만 사용합니다. 실패해도 커서와 보고서를 보관합니다. 장기 비활성 저장소는 GitHub가 스케줄을 중지할 수 있으므로 Actions의 활성 상태를 확인하세요.

## 리뷰 수집의 한계

리뷰 API는 비로그인으로 정렬당 약 10페이지(100건)까지만 응답하고 그 뒤로 `loginRequired`를 준다.
로그인을 우회하지 않으므로 한 번에 받을 수 있는 양은 상품·정렬당 그 정도가 상한이다.
여러 상품을 연속으로 수집하면 서버가 긴 대기를 요구하고(`RateLimited`), 크롤러는 거기서 멈춘다.

그래서 리뷰는 한 번에 다 받는 것이 아니라 여러 세션에 나눠 쌓는다. 커서는 `.pipeline-cache`에
체크포인트되므로 다음 실행이 멈춘 지점부터 이어간다. 수집 간격은 `--delay`로 늘릴 수 있고,
2.5초에서도 레이트 리밋에 걸린 적이 있다.

2026-09-19 기준 저장된 리뷰는 25,818건이고, 원본에 남아 있는 미수집분은 상품 29개에 5만 건 이상이다.

## 추천 점수의 의미

Gemini 호출 없이 한국어 리뷰의 명시적인 긍정·부정 표현을 집계하는 `rules-ko-v1` 기준입니다. 모델 정확도가 검증된 학습 추천기는 아니며, 문맥·반어·복잡한 부정을 놓칠 수 있습니다.

항목별 근거가 3건 미만이면 점수는 `null`입니다. 피부타입 지표는 같은 피부타입 작성자의 평점을 표본 수에 따라 보정한 값이며 의학적 안전성·적합 확률이 아닙니다. 피부 고민이 있다는 자기소개를 제품 효능으로 계산하지 않습니다. 호수는 두 가지로 나눠 다룹니다. 옵션에 21/23/25가 명시된 제품은 그 값을 그대로 쓰고, 그렇지 않은 제품은 **그 제품 안에서의 밝기 순서**만 사용합니다. 남성 커버로션·쿠션은 브랜드마다 `1호/2호`, `01 라이트베이지/02 내추럴베이지`처럼 자체 표기를 쓰기 때문입니다. 브랜드의 1호가 21호와 같다고 주장하지 않으며, "이 제품의 2종 중 밝은 쪽"까지만 말합니다. 그래서 상대 순서로 얻는 가점은 명시된 호수보다 낮게 잡혀 있습니다.

순서는 옵션명에 적힌 것만으로 정합니다. 번호는 `호` 표기나 순수 숫자 코드, 또는 색상어가 함께 있을 때만 호수로 인정합니다(`01 코어썸`처럼 번호가 붙은 제품 변형은 제외). 색상어 순서는 라이트·아이보리 → 내추럴·미디엄 → 베이지 → 샌드·앰버 → 탄·딥이며, 모든 옵션이 서로 다른 단계로 갈릴 때만 사용합니다. `살몬 베이지`와 `그린 베이지`는 밝기가 아니라 색 보정 목적이라 순서를 만들지 않고, 용량·기획 변형만 있는 경우도 호수로 보지 않습니다. 현재 옵션을 확보했다면 과거 리뷰 옵션보다 우선합니다. 품절 옵션도 라인업에 남기며, 판매 중 옵션이 없으면 품절 표시와 함께 가장 가까운 호수를 추천합니다.

프로필에 분석 버전·리뷰 수·항목별 근거 수·근거 리뷰 ID·입력 해시·분석 시각을 저장합니다. 점수와 고민 태그는 각각 근거가 된 리뷰 ID를 함께 저장하므로, 상세 화면에서 "근거 리뷰 보기"로 그 주장이 어떤 리뷰에서 나왔는지 확인할 수 있습니다. 입력이 동일하면 재계산을 생략합니다. 저장하는 메타데이터의 형태가 바뀌면 `METADATA_REVISION`을 올려 재계산을 유도합니다. 점수 산출 규칙이 그대로일 때 `VERSION`은 유지되므로 배포된 화면이 구버전 프로필로 잘못 표시되는 구간이 생기지 않습니다. 중요도 1은 해당 항목의 가중치 0이며 낮은 품질을 선호한다는 의미가 아닙니다.

## 브랜드 호수와 21/23/25의 대응

`pipeline/shade_mapping.py`는 브랜드 자체 호수를 21/23/25 기준에 대응시키는 **진술**을 모읍니다. 쿠션 호수만 나오는 문장("저는 23호를 쓰는데")은 글쓴이 피부 이야기지 제품 설명이 아니므로 버리고, 브랜드 호수와 쿠션 호수가 한 문장에 같이 나올 때만("2호 라이언(23호)", "22-23호 분들은 2호로") 매핑으로 봅니다.

저장된 리뷰 기준 측정치(2026-09-18, 리뷰 25,664건 / 문장 97,373개):

| 항목 | 값 |
|---|---|
| 쿠션 호수(19~29호)를 언급한 문장 | 638개 |
| └ 매핑 진술로 인정 | 150개 |
| └ 자기소개 등으로 기각 | 488개 (76.2%) |
| 추출된 (브랜드 호수 → 쿠션 호수) 쌍 | 184개 |
| 쿠션 호수를 언급한 리뷰 | 547건 |

한 문장에서 쌍이 둘 이상 나올 수 있으므로 쌍의 수(184)와 문장 수(150)는 다릅니다. 커밋 `328c270`의 메시지에는 이 수치가 "638개 문장 중 454개가 자기소개"로 잘못 적혀 있습니다. 638에서 쌍의 수를 뺀 값이라 성립하지 않으며, 위 표가 정확한 값입니다.

집계는 최빈값이 아니라 중앙값을 씁니다. 이웃한 호수(21호와 22호)는 무작위 불일치가 아니라 한 칸 차이의 근사 합의이기 때문입니다. 진술이 5건 미만이거나, 서로 다른 브랜드 호수가 같은 쿠션 호수로 수렴하거나(구매자가 둘을 구분할 수 없음), 밝은 번호가 어두운 번호보다 어둡게 나오면 채택하지 않습니다.

이 모듈은 DB에 쓰지 않고 `.pipeline-cache/shade-mapping-report.json`만 만듭니다. 잘못된 절대 호수는 호수 정보가 없는 것보다 구매자에게 나쁘기 때문에, 반영 여부는 리포트를 보고 판단합니다. 저장된 리뷰만으로는 현재 1개 상품이 채택됩니다.

```powershell
python pipeline/shade_mapping.py              # 저장된 리뷰에서
python pipeline/shade_mapping.py --youtube    # 유튜브 설명·댓글까지 (YOUTUBE_API_KEY 필요)
```

유튜브는 공식 Data API v3의 검색·설명·댓글만 사용합니다. 남의 영상 **자막은 공식 API로 받을 수 없어**(영상 소유자 OAuth 필요) 음성으로만 말한 호수 조언은 닿지 않습니다. 검색은 상품당 100 유닛이고 기본 일일 할당량이 10,000이라 탐색 상품 수를 제한하고 사용량을 기록합니다. 키는 `YOUTUBE_API_KEY` 환경변수에서만 읽으며 저장소에 두지 않습니다.

## 검증

상품의 원본 소분류는 `profile_metadata.source_category`에 보존됩니다. 퀴즈는 전체 얼굴 커버를
묻기 때문에 프라이머·파우더·쉐이딩·컨실러는 추천에서 제외하고 카탈로그에는 남깁니다.
기존 상품의 소분류를 채우려면 아래 순서로 상품만 다시 수집한 뒤 프로필을 생성합니다.
상품 수집은 수동이며 자동 프로필 갱신 일정은 그대로입니다. 저장소 루트에서 실행합니다.

```powershell
Push-Location code/7_advanced_recommender
../../.venv/Scripts/python.exe -m scraper.crawler --products-only --write --delay 5
../../.venv/Scripts/python.exe run_pipeline.py --profiles-only --write
../../.venv/Scripts/python.exe ops.py health
../../.venv/Scripts/python.exe ops.py status
Pop-Location
```

각 실행의 오류·중단 보고서를 확인합니다. 접근 제한으로 일부 상품만 갱신됐다면 소분류 전환도
부분 적용 상태입니다. `METADATA_REVISION=6`은 프로필 재생성을 유도하고 `rules-ko-v1`은 유지합니다.
품절 호수도 추천할 수 있습니다(2026-09-19 사용자 확인). 판매 중 옵션을 우선하되 모두 품절이면
원래 라인업에서 가장 가까운 호수를 추천하며, 카드·상세 화면에서 품절 상태를 표시합니다.

`ops.py verify`는 웹 의존성이 없어서 검사를 생략한 경우에도 실패합니다. `ops.py health`는
공개 상품·리뷰 조회 성공과 작성자 열의 명시적 권한 거부를 별도로 확인하고, 배포 HTML과
연결된 JS 파일에서 서버 키를 검사합니다. 지연 로딩 파일까지 포함한 전체 정적 산출물 검사는
빌드 후 `check-bundle.mjs`가 담당합니다. 네트워크 실패는 보안 검사 성공으로 간주하지 않습니다.
커밋을 이미 푸시했다면 `ops.py crosscheck --base <작업 전 커밋>`을 사용하세요.
`origin/main`이 현재 코드와 같으면 비교할 변경이 없다는 경고를 표시합니다.

```powershell
.venv/Scripts/python.exe -m unittest discover -s code/7_advanced_recommender/tests -v
cd code/7_advanced_recommender/web
npm ci
npm test
npm run eval
npm run lint
npm run build
```

`npm run eval`은 `tests/fixtures/personas.json`의 페르소나 12명을 실제 화면과 같은 `selectRecommendations`로 정렬해, 사용자가 건 조건을 결과가 지키는지 측정합니다. 관련도 정답이나 클릭 로그가 없으므로 NDCG·Recall이 아니라 **제약조건 충족률**과 **근거 추적률**을 봅니다. 하드 조건(구버전 프로필, 분석 리뷰 최소치, 사용 방식 필터) 위반이나 결과 0건이면 실패하고, 나머지 비율은 변경 전후 비교용으로 보고만 합니다. 커밋된 `tests/fixtures/catalog-snapshot.json`으로 돌기 때문에 CI에서 DB 접근이 필요 없습니다. 스냅샷 갱신은 `npm run snapshot`(공개 키 필요)입니다.

웹 빌드 전 환경변수와 빌드 후 정적 파일에서 관리자 키를 검사합니다. CI에는 실제 DB 키 대신 공개용 형식의 테스트 값을 사용합니다. 상품 삭제와 리뷰 재귀속을 수행하던 `merge_variants.py`는 중지했습니다.
