### 1.2 주장의 근거 추적 + 추천 평가 하네스 (`4077893`)

**근거 리뷰 연결**
- `profiles.py`가 고민(concern)별 근거 리뷰 ID를 수집한다. 속성별 `evidence_review_ids`는 이미 있었고, 고민 태그에만 근거가 없었다.
- `METADATA_REVISION`을 도입해 `input_hash`에 포함시켰다. 메타데이터 형태가 바뀌면 저장된 프로필이 자동 재생성된다.
  `VERSION`은 건드리지 않으므로 배포된 화면이 "구버전 프로필"로 인식해 깨지는 구간이 없다. **이 구분은 유지할 것.**
- 상세 모달에서 점수·고민마다 "근거 리뷰 N건 보기"로 실제 리뷰를 확인할 수 있다.
- 59개 상품 백필 완료. 공개 키로 근거 리뷰 조회가 되는지(RLS 권한) 실제 확인했다.

**평가 하네스**
- `selectRecommendations`를 `page.tsx`에서 `lib/recommendation.ts`로 추출했다. 평가가 실제 화면과 같은 정렬을 측정하게 하려는 것이다. **인라인으로 되돌리지 말 것.**
- `npm run eval` — 페르소나 12명(`tests/fixtures/personas.json`)을 커밋된 카탈로그 스냅샷으로 정렬해 제약조건 충족률을 측정한다.
- 관련도 정답·클릭 로그가 없어 NDCG/Recall은 근거가 없다. 하드 조건(구버전 프로필, 최소 분석 수, 사용 방식 필터) 위반만 실패 처리하고 나머지 비율은 비교용 보고만 한다.
- CI(`quality.yml`)에 추가했다. 스냅샷으로 돌기 때문에 DB 접근이 필요 없다.

**결과**: 호수 보유 상품 2개 → 26개. 페르소나 기준 "쓸 수 있는 호수 없음" 95.2% → 34.5%.

### 1.7 자동 교차 검수 (Claude → Codex)

`python ops.py crosscheck`가 `codex review --base origin/main`을 실행한다.
Codex가 `AGENTS.md`를 스스로 읽으므로 불변조건이 그대로 검수 기준이 된다
(`codex review`는 `--base`와 커스텀 프롬프트를 같이 받지 못한다).
실제 호출로 코덱스까지 도달하는 것을 확인했고, 현재는 사용량 한도 소진으로 대기 상태다.

`.mcp.json`에 `codex mcp-server`를 등록해 두었다. Claude Code 재시작 후 확인이 필요하다.

**Antigravity는 이 고리에 못 들어온다.** 서브커맨드가 `chat`·`serve-web`·`tunnel`뿐이고
`chat`은 GUI에 프롬프트를 던질 뿐 결과를 반환하지 않는다. 이 PC의 Orca(1.4.205)도 마찬가지로
지원하지 않는다 — 234개 명령 스키마에 antigravity가 없고 `worker-start --model`은
Claude·Codex·Cursor만 받는다.

## 3. 남은 과제 (우선순위)

1. **베이스 메이크업 소분류 목록 실측** — 중분류만 확인했고 소분류는 `BB/CC` 하나만 직접 봤다.
   `catalog-details.json`에 `lowerCategoryName`을 같이 기록하도록 고치면 다음 실행에서 자동으로 모인다.
2. **샌드/앰버 밝기 분리** — 현재 색상어 사전이 둘을 같은 단계로 묶어 `블랙몬스터 비비크림
   (샌드베이지/앰버베이지)`이 순서를 못 만든다. 통상 샌드 < 앰버다. 1개 상품이 복구된다.
3. **톤로션 경로 호수 커버리지** — 쿠션 83~92% 대비 톤로션 33~42%로 낮다.
   입문자가 집는 카테고리라 체감 영향이 가장 크다. 2.1 수집이 끝나면 얼마나 개선되는지 먼저 측정할 것.
4. **추천 품질 검증셋** — 현재는 제약조건 충족률만 본다. 사람 평가 라벨이 생기면 NDCG/Recall로 확장 가능.
5. **유튜브 매핑 실행** — 키 재발급 후 `python pipeline/shade_mapping.py --youtube`.
   측정상 수확량은 낮을 것으로 보인다(리뷰만으로 1개 채택). 자막 접근 불가가 한계.

## 4. 검수 시 봐야 할 것

- `pipeline/profiles.py`의 `shade_lineup()` — 오탐 방지 규칙이 과한지/부족한지가 핵심 판단 지점이다.
  현재 26/59가 라인업을 갖는다. 규칙을 풀면 오탐이, 조이면 누락이 늘어난다.
- `lib/recommendation.ts`의 호수 가점 설계 — 명시 호수 +15, 상대 순서 최대 +10. 이 격차가 타당한지.
- `shade_mapping.py`의 가드 3종 — 특히 "같은 쿠션 호수로 수렴하면 기각"이 비레디 쿠션을 떨어뜨린다.
  진술 수가 35/37건으로 많은 제품이라 아깝지만, 2호·3호를 구분해줄 수 없으면 구매에 도움이 안 된다는 판단이다.
- 테스트 43개(백엔드) + 15개(웹). 회귀 테스트가 의도를 문장으로 담고 있으니 먼저 읽으면 빠르다.

## 5. 이 세션에서 바로잡은 내 오류

검수 시 참고하도록 남긴다.

- "톤로션은 호수 개념이 없다" — 데이터를 안 보고 한 추론이었고 틀렸다. 실제로는 호수가 있는데 시스템이 버리고 있었다.
- 평가 지표 `traceable_rate`가 주장 없는 상품에 대해 빈 배열의 `every`로 공허하게 참이 되어 100%가 부풀 수 있었다.
  주장 있는 상품만 분모로 바꾸고 `주장없음` 열을 추가했다.
- 매핑 통계에서 리뷰/문장/쌍 단위를 섞어 "638개 중 454개"라고 잘못 적었다. 커밋 `328c270` 메시지에 그대로 남아 있고,
  README와 위 1.4에 정확한 값이 있다.
