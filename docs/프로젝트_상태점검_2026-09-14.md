# 남성 화장품 추천 프로젝트 상태 점검

점검일: 2026-09-14 (KST)

## 판단

상품 수집 → Supabase 적재 → Gemini 리뷰 분석 → 설문 기반 추천 → 웹 배포까지 구현된 프로젝트다. 현재 서비스는 동작하지만, **관리자 키 공개 노출, 자동 수집 중단, 추천 근거 데이터 부족**을 먼저 해결해야 한다. 기능 확장에 앞서 운영과 추천 품질을 복구하는 업데이트가 필요하다.

점검은 로컬 코드, GitHub Actions 이력, Supabase 읽기 조회, 공개 배포 파일, 로컬 빌드·린트, 부작용 없는 함수 재현으로 수행했다. 운영 DB 쓰기·삭제, 키 변경, 크롤러 전체 실행, 유료 Gemini 분석, 배포는 수행하지 않았다. 기존 사용자 변경 파일은 유지했다. 키 원문과 리뷰 작성자 정보는 보고서에 기록하지 않았다.

## 1. 현재 구현 구조

```text
올리브영 상품 목록·리뷰 API
  → code/7_advanced_recommender/scraper/crawler.py
  → Supabase products / reviews
  → pipeline/build_profiles.py (Gemini + 성분 규칙 + 리뷰 집계)
  → products의 점수·피부고민·호수 프로필
  → web/src/app/page.tsx (설문 + 필터 + 가중 점수 계산)
  → Next.js 정적 웹 / Vercel, 별도 GitHub Pages 워크플로
```

- 현재 추천 방식은 **LLM으로 추출한 상품 특성에 규칙과 가중치를 적용하는 콘텐츠 기반 추천**이다. 현재 웹 경로에서 사용자 행동을 학습하는 협업 필터링이나 학습된 랭킹 모델은 확인되지 않았다.
- `code/1`~`4`는 수집·전처리·시장 분석 자료, `code/5_recommendation_system`은 이전 추천 버전이다.
- README와 운영 가이드는 시장 분석·Streamlit 버전 중심이어서 현재 Next.js·Supabase 운영 방법과 맞지 않는다.
- 상품·리뷰 기본키와 upsert, 리뷰 외래키, 별도 분석 파이프라인, 실제 배포까지 갖춘 점은 유지할 기반이다.

## 3. 우선순위별 발견 사항

### P0. 배포된 프런트엔드에 Supabase 관리자 키 노출 — 확인됨

- 로컬 웹의 `NEXT_PUBLIC_SUPABASE_ANON_KEY` 값은 이름과 달리 JWT `role=service_role`이었다.
- 공개 배포 JavaScript `/_next/static/chunks/2e87ea4ec4faa03e.js`에서도 `service_role` 키를 확인했다.
- `web/src/lib/supabase.ts:3`~`6`에서 이 키를 브라우저 클라이언트에 전달한다.
- `.github/workflows/static.yml`도 쓰기 작업에 사용하는 `secrets.SUPABASE_KEY`를 `NEXT_PUBLIC_SUPABASE_ANON_KEY`에 주입한다.

**영향:** 방문자가 관리자 키를 획득할 수 있다. Supabase 공식 문서상 `service_role`은 RLS를 우회하는 서버 전용 자격증명이다. 실제 악용 여부나 쓰기 가능 범위를 확인하기 위한 변경 요청은 하지 않았다.

**조치:** 공개용 publishable/anon 키와 서버 쓰기용 키를 분리하고, 공개 읽기 범위와 쓰기 차단 정책을 설정한다. 프런트엔드를 재배포하면서 노출 키를 폐기·재발급해야 한다. 키 교체에 따라 크롤러·파이프라인의 서버 비밀값도 함께 갱신한다. 기존 배포에 있던 키는 소스에서 제거하는 것만으로 무효화되지 않는다.

근거: [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

### P1. 자동 갱신이 중단됐고, 수집 후 프로필 갱신도 연결되지 않음

- 수집 워크플로는 주 1회 월요일 09:00 KST로 정의되어 있으나 현재 `disabled_inactivity` 상태다.
- 최근 확인 가능한 6회는 모두 `Run Crawler` 단계에서 실패했다.
- 최신 실패 실행의 로그 조회는 HTTP 410으로 실패했다. **과거 실패의 정확한 예외는 확인하지 못했다.**
- 워크플로 설치 목록은 `curl_cffi supabase python-dotenv`인데 크롤러가 import하는 `bs4`의 패키지 `beautifulsoup4`가 빠져 있다. 재현 가능한 의존성 선언을 먼저 보완해야 한다.
- 워크플로는 `crawler.py`까지만 실행한다. 신규 리뷰를 수집해도 `build_profiles.py`가 이어서 실행되지 않아 추천 프로필은 자동 갱신되지 않는다.
- 루트 requirements에는 `streamlit, pandas, numpy, plotly`만 있다. 현재 크롤러·Gemini 파이프라인 전체 환경을 복원할 수 없다.

근거: `.github/workflows/crawler-schedule.yml`, `requirements.txt`, [최근 수집 실행](https://github.com/MOON001208/MANS-BEAUTY/actions/runs/25648920209).

### P1. 증분 수집에 신규 리뷰 누락과 페이지 제한 문제가 있음 — 재현됨

- `scraper/crawler.py:255`는 유용성 순서 `USEFUL_SCORE_DESC`를 사용한다.
- 같은 파일 `:276`~`278`은 기존 리뷰를 만나면 조건에 따라 즉시 종료한다. 유용성 순서는 시간순이 아니므로 이후 페이지·행에 신규 리뷰가 남을 수 있다.
- 함수에 가짜 API 응답 `[기존 리뷰, 신규 리뷰]`를 전달한 재현에서 신규 리뷰 반환 건수는 **0건**이었다.
- `get_existing_review_ids()` (`:225`)에는 페이지 순회가 없다. 실제 동일 형식 조회에서 DB 리뷰 **4,117건 중 1,000건만 반환**됐다.
- `new_needed`는 원본 리뷰 총수와 일부 조회한 기존 ID 수를 비교하므로 잘못된 재수집 판단을 할 수 있다. 총 건수 비교만으로는 기존 리뷰 편집·삭제도 감지하지 못한다.

**조치:** ID 조회 페이지 순회, 원본 API의 실제 지원 정렬 검증, 수집 커서와 중첩 조회 구간, ID 기준 중복 제거, 주기적 정합성 검증을 도입한다. 특정 정렬 코드가 현재 지원된다고 가정해 변경하면 안 된다.

참고: [Supabase Python select 기본 1,000행 제한](https://supabase.com/docs/reference/python/select).

### P1. API 실패가 데이터 초기화나 성공으로 처리될 수 있음

- `fetch_product_stats()`는 실패 시 리뷰 수·평점을 0으로 반환한다 (`crawler.py:170`).
- 전성분 수집 실패는 빈 문자열이 된다. 상품 upsert는 이를 그대로 저장해 기존 값도 덮어쓸 수 있다 (`:327`).
- 저장 함수가 예외를 기록하고 삼킨 뒤, main에서는 저장 완료 로그와 건수를 증가시킨다.
- 목록 페이지는 HTTP 상태를 검증하지 않고 HTML을 파싱한다. 오류 페이지를 상품 0개인 정상 종료로 처리할 수 있다.

**조치:** 미수집·실패·실제 0을 구분하고, 성공한 필드만 갱신한다. 작업별 시도/성공/실패 수, 커서, 시작/완료 시각을 남기며 필수 단계 실패는 프로세스 실패로 전달한다.

### P1. Gemini 모델과 오류 처리 업데이트 필요

- `pipeline/build_profiles.py:66`은 `gemini-2.0-flash-lite`에 고정되어 있다. Google 공식 문서의 해당 모델 종료일은 **2026-06-01**이다. 이번 점검에서는 유료 모델 호출을 수행하지 않았다.
- `_call_gemini_batch()` (`:183`)가 API/JSON 오류를 내부에서 잡고 기본값을 반환하므로 외부 재시도 루프가 해당 오류를 인식하지 못한다.
- 모든 값이 null이면 `safe_mean()`이 3.0을 저장한다 (`:299`). 분석 실패가 정상적인 3점 상품으로 보일 수 있다.
- 결과를 리뷰 ID로 연결하지 않고 배열 위치로 연결하며, 반환 수가 다르면 잘라내거나 채운다. 순서 변경·누락 시 다른 리뷰의 속성이 붙을 수 있다.
- 리뷰별 분석 결과, 모델/프롬프트 버전, 분석 상태와 근거 건수의 영속 저장이 없어 재실행 비용과 결과 추적에 취약하다.

**조치:** 지원 중인 모델을 설정값으로 관리하고 작은 검증셋으로 교체 품질을 비교한다. JSON 스키마·점수 범위·리뷰 ID를 검증하고 실패 결과는 기존 프로필을 덮어쓰지 않는다. 새 리뷰만 분석하도록 리뷰별 결과를 저장한다.

근거: [Google Gemini 종료 일정](https://ai.google.dev/gemini-api/docs/deprecations).

### P1. 전성분 부족으로 추천의 가장 큰 가중치가 근거 부족 상태

- 원본 전성분이 없는 상품은 53/55개다.
- 이 중 52개는 확인한 지성·건성·민감성 호환 점수가 모두 기본값 0.5다. 나머지 1개는 원본 성분 없이 비기본 점수가 남아 있어 근거 추적이 필요하다.
- 웹 추천은 피부 호환성에 50점을 배정한다 (`page.tsx:58`). 많은 상품에서 이 기준이 개인화에 기여하지 못한다.
- 성분 함수는 문자열 부분 일치와 개수 비율로 `저자극`, `자연유래`, 호환 점수를 결정한다. 화면은 이를 호환 **%**로 표시하지만, 확률을 보정하거나 실제 피부 반응으로 검증하는 과정은 코드에서 확인되지 않았다.

**조치:** 원본 성분 수집 성공률부터 복구한다. 미확인 값은 미확인으로 표시하고, 규칙 점수와 검증된 효능·확률을 구분한다. 성분 정규화·매칭 근거·원본 수집일을 저장한다.

### P1. 추천 특성 생성과 사용자 입력 해석에 오류 — 일부 재현됨

1. **색상 부분 일치 충돌:** `get_shade_from_option()` (`build_profiles.py:274`)은 일반 단어 `베이지`를 먼저 검사한다. `샌드베이지`, `앰버베이지`가 내부 매핑의 25호 대신 **23호**로 반환됐다. 실제 호수는 브랜드·상품별 옵션 매핑으로 관리할 필요가 있다.
2. **고민 보유를 적합성으로 해석:** `skin_concern_counter` (`:313`~`334`)는 리뷰 작성자의 고민과 언급 빈도를 긍·부정 구분 없이 집계한다. 지성·여드름 사용자 부정 리뷰 10개만 넣은 함수 재현에서도 `suitable_concerns=['acne']`, `suitable_skin_types=['oily']`가 나왔다. ‘누가 샀는가’와 ‘누구에게 효과가 있었는가’를 분리해야 한다.
3. **중요도를 목표 성능으로 처리:** 설문은 1점을 ‘신경 안 씀’으로 설명한다 (`page.tsx:281` 근처). 점수 함수는 사용자 입력과 상품 성능 점수의 절대 차이를 계산한다 (`:76`). 따라서 지속력을 중요하지 않게 선택하면 지속력 낮은 제품에 더 높은 일치 점수를 줄 수 있다. 중요도라면 가중치로 사용해야 한다.
4. **원본 총리뷰 수를 분석 신뢰도로 사용:** 추천 후보 제한은 `products.review_count >= 200`이다 (`page.tsx:580`). 원본 총수가 2,097인데 DB 저장 리뷰가 0인 상품도 확인됐다. 수집·분석 근거 건수와 별도 관리해야 한다.

### P1. 상품 병합 실패 시 리뷰 유실 위험

- `scraper/merge_variants.py:131`의 리뷰 재매핑이 실패해도, 뒤의 상품 삭제 (`:142`)를 실행한다.
- 기본 스키마의 리뷰 외래키는 `ON DELETE CASCADE`다. 해당 제약이 적용된 DB라면 재매핑되지 않은 리뷰도 삭제될 수 있다.
- 여러 요청 사이에 트랜잭션이 없다. 원본 상품 ID와 병합 매핑도 별도로 보존하지 않아, 재수집 시 변형 상품이 되살아나거나 리뷰가 다시 이동할 수 있다.

**조치:** 원본 상품·옵션을 보존하고 canonical 상품 그룹을 별도로 만든다. 필요한 병합은 트랜잭션 안에서 실행하고, 실패 시 전체 롤백과 전후 리뷰 수 검증을 보장한다. 이번 점검에서는 병합을 실행하지 않았다.

### P2. 스키마·지표 정의·프런트엔드가 일치하지 않음

- `code/supabase_schema.sql`에는 현 코드가 사용하는 `ingredients_raw`, `product_type`, 프로필 점수, `skin_tone`, `skin_trouble` 등의 필드 추가가 없다. 새 DB를 코드만으로 복원하기 어렵다.
- 저장소 SQL에서 RLS 활성화와 정책 정의를 찾지 못했다. 운영 DB의 실제 정책은 이번 접근으로 확인하지 못했으며, 정책이 없다고 단정하지 않는다.
- `product_review_summary`, `product_category_rank`는 SQL 파일이 있지만 현재 REST 조회는 404였다. 미적용 또는 API 미노출 여부를 DB에서 구분해야 한다.
- 상품 55개 모두 `products.review_count`와 실제 저장 리뷰 수가 달랐다. 원본 총수와 부분 수집 건수는 원래 다를 수 있으므로 **차이 자체를 곧바로 데이터 손상으로 해석하면 안 된다.** 필드를 원본 총수·저장 수·분석 수로 나누어야 한다.
- 프런트엔드는 API의 `error`를 처리하지 않는다 (`page.tsx:443`, `:587`, `:607`). 장애 시 빈 결과 또는 이전 추천 결과가 남을 수 있다.
- 리뷰 모달은 높은 별점 우선 15개다. 추천 근거를 보여주려면 긍정·부정 리뷰를 함께 제공하는 편이 적절하다.
- 검색 요청 취소/응답 순서 보호가 없어 빠른 입력이나 화면 전환 시 늦게 온 이전 요청이 결과를 덮어쓸 수 있다.

현재 로컬 Python은 3.13.12, Node는 24.12.0이다. CI 설정은 Python 3.10, Node 20이다. 로컬에는 `curl_cffi`, `supabase`, `pytest`가 설치되어 있지 않다. 기존 test 이름의 파일은 주로 크롤링 디버그 스크립트이며, 현재 추천 경로의 자동 회귀 테스트·정량 평가 체계는 확인되지 않았다.

전체 크롤링, 실 Gemini 분석, 익명 키 기반 RLS 검증, 브라우저 전체 설문 클릭 테스트는 수행하지 않았다. 따라서 최신 올리브영 페이지/API와 크롤러의 실제 호환성 및 화면 전체 상호작용은 별도 확인 항목이다.

## 5. 업데이트 권장 순서와 완료 기준

### 1단계 — 보안 복구

- 공개 키와 서버 키 분리, RLS/권한 설정, 노출 키 폐기·재발급, 영향받는 환경변수 교체 및 재배포.
- 완료 기준: 공개 배포 번들에 관리자 키가 없고, 공개 읽기는 필요한 범위만 허용되며 브라우저 역할의 쓰기는 차단됨을 확인.

### 2단계 — 수집·적재 재현성과 갱신 복구

- 현재 버전용 의존성·실행 명령·DB 마이그레이션 정리.
- 페이지 제한, 증분 중단, 실패 시 덮어쓰기, 병합 트랜잭션 문제 수정.
- 작업 이력·실패 알림과 수집 후 프로필 업데이트 연결. 복구 후 스케줄 재활성화.
- 완료 기준: 일부 상품으로 수집→재실행 시 중복 없음→신규 리뷰 반영→프로필 갱신을 확인하고, 실패가 성공으로 기록되지 않음.

### 3단계 — 추천 신뢰도 개선

- 성분 데이터 복구, 브랜드별 옵션 정규화, 중요도 계산 수정.
- 피부 고민 보유와 긍정 효능·부정 반응을 분리하고, 리뷰별 분석 결과·근거 건수·버전 저장.
- 기존 점수 대비 추천 품질을 비교할 검증셋 구성. 사용자 로그가 없으면 먼저 사람 평가와 제약조건 충족률을 사용한다. 관련도 정답이나 클릭 데이터가 확보되면 NDCG@K·Recall@K 등으로 확장한다.
- 완료 기준: 호수 오분류·부정 반응을 적합으로 오해하는 사례가 회귀 테스트에서 차단되고, 추천 이유가 실제 근거 리뷰와 연결됨.

### 4단계 — 사용성·운영 문서 정리

- 조회 오류·빈 결과·재시도, 검색 요청 경합 처리, 최신 수집일·분석 표본 수 표시.
- 소규모 브랜드는 일괄 200건 컷보다 데이터 충분성·불확실성을 구분해 노출하는 정책을 평가한다.
- 현재 서비스 중심 README, 구버전 보관 구분, 배포 대상 명확화, CI 린트·빌드·핵심 회귀 테스트 추가.

**첫 업데이트 범위로는 1~2단계가 적절하다. 현재 구조를 살리면서 데이터와 운영을 복구한 뒤, 추천 알고리즘 고도화의 효과를 측정할 수 있다.**
